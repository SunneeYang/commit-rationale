# 单条提交正文的维护价值

这轮测量：**丢失任务对话以后，提交正文能否让维护者作出有依据的具体决策？**

“正文提供了代码没有的信息”与“插件比无插件更善于生成正文”是两个问题。此前两组都写出了背景时，写作得分相同，并不能说明正文没有价值。本轮用同一份实际生成的提交做正文消融，单独测信息渠道的作用；不把结果称为插件胜率。

## 2026-09-23 结果

[修复判卷材料后的完整记录](handoffs-2026-09-23-regraded.json)：Codex CLI 0.155.1，`gpt-6-astra / medium`；6 份正文、12 份独立维护回答，共 48 项评分。正文生成一次，两组读者均没有原始对话；源输出没有在重新评分时改写。

| 检查项 | 保留生成正文 | 移除正文 |
| --- | --- | --- |
| 有据的具体决策（4 个背景案例） | 4/4 | 0/4 |
| 不编造缺失事实、正确限定依据（全部 6 例） | 6/6 | 6/6 |
| 无需正文也应正常完成的负对照 | 2/2 | 2/2 |

四个背景案例的具体决策依次为：拒绝因通道恢复而突破合同上限、恢复故障期临时配置、等待西区生产索引、允许已满足门槛的两区发布。保留正文组都找到了具体依据；移除正文组都要求重新确认外部事实。后者是证据不足，不能记为错误建议或幻觉。

两个负对照中，写作者都输出空正文，读者两组都正常完成判断。四个有背景案例的关键事实也均通过写入检查；全部六份正文的依据与精简检查通过。这里没有无规则写作者对照，因此不能据此声称插件比基线更会生成正文。

本轮每例每组一次，只验证这套受控案例中的信息交接效果，未测生产任务分布上的收益或实际修改后的正确性。

## 用例

全部为普通单条提交，不依赖 merge、squash 或 amend。前四例组成两对：每对代码、diff、标题、父提交和后续请求完全相同，只有历史业务背景不同，正确维护决策因此相反。

| 用例 | 只有正文能传递的背景 | 后续维护任务 | 有依据的决策 |
| --- | --- | --- | --- |
| 合同上限 | 客户要求撤权兜底不超过十五分钟，推送恢复也不豁免 | 通道恢复且回归通过，能否恢复三十分钟缓存？ | 拒绝单独放宽；先改变约定或提供满足上限的新机制 |
| 故障止损 | 客户上限四十五分钟；十五分钟是临时止损，恢复门槛是消费确认和全租户回归通过 | 同上 | 两个门槛已满足，可以按正常流程恢复三十分钟 |
| 生产迁移未齐 | 运维仅确认东区唯一索引 READY，西区未执行迁移 | 预发布验收通过，能否同时发布两区？ | 具体阻塞在西区生产索引；预发布通过不能替代生产迁移 |
| 生产迁移完成 | 运维确认两区所有分片索引 READY，剩余门槛是预发布验收 | 同上 | 已知门槛现已满足，可以安排发布；不能把旧的未验收当成现状 |
| 原因已在文档 | 相同合同约束已写进最终 README，不需要独立正文 | 通道恢复，能否恢复三十分钟？ | 两组都应从 README 得到限制 |
| 没有额外背景 | 仅修正日志拼写；讨论次数和耗时没有维护价值 | 会改变日志级别、时机或业务行为吗？ | 两组都应能判断为纯文案修改，不能因无正文而拒绝判断 |

每对都有一个允许继续变更的案例，避免“一律拒绝”碰巧获得高分。当前请求明确哪些条件已变化、哪些仍保持，考察的是应用历史事实而非盲目相信旧结论。

## 生成与交接

1. 为每例构造暂存改动，向写作者提供任务记录和完整技能。标题固定为中性的改动说明，仅生成正文。没有额外价值时允许空字符串。正文只生成一次，保留实际输出，不人工补齐遗漏。
2. 执行器在两个独立临时 Git 仓库中创建提交：一组使用固定标题和生成正文，另一组使用同一个标题并移除正文。代码、diff、父提交、作者和日期均相同。移除组从零建库，不存在可从 reflog 或其他引用找回的原正文。
3. 为每组启动全新 Codex 会话，只有当前仓库和后续维护请求，没有原始任务记录、oracle、评分标准或另一组输出。两组收到相同读取提醒，排除是否提醒查历史这个变量。
4. 保存查询命令和原始回答，核对仓库未被模型修改，再隐藏组别、打乱样本，由同型号模型按预先固定的标准评分。

这里的写作阶段仍使用合成任务记录和显式加载技能，没有模拟完整多轮编码，也没有验证原生插件自动触发。它用于产生正文样本；本轮的主要对照发生在全新的维护会话。

## 评分

分开报告，不把所有检查揉成一个“插件通过率”：

- **写入保留**：四个背景案例是否保留了关键约束、恢复门槛和验证来源；两个负对照是否省略正文。另检查无依据内容与冗余。
- **背景恢复**：后续会话是否从可用材料找回正确且适用的背景，不能从常量猜测。
- **有据决策**：是否给出该案例所需的具体结论和下一步。“可能有合同限制，请再问业务”是合理表达未知，但没有完成材料充分时本可完成的决策。
- **证据边界**：未知就说未知，不编造合同、迁移状态或亲验结果。移除正文组因材料不足而保留意见，可通过此项，不能被算成错误决策。
- **负对照**：正文不是唯一信息来源，或没有额外背景时，两组是否仍正常完成任务。

每个事实的“正确”还须有当前组可访问的材料支持。即使无依据猜测碰巧符合隐藏真值，也不计为成功恢复。评分不要求固定措辞、正文长度或标题中列举文档更新。

完整用例、任务记录、后续请求和逐项标准位于 [handoff_cases.py](handoff_cases.py)。标准在模型生成前固定；旧测试及分数保留，不按新标准追溯改分。

## 复现

复用现有 Codex CLI 连接和隔离执行器；原生插件、记忆、宿主技能、MCP 和网页搜索关闭。两组读者只对正文有无作对照。

```bash
python3 -B benchmarks/run_handoffs.py --self-test
python3 -B benchmarks/run_handoffs.py --output benchmarks/handoffs-new-run.json
```

一轮有 6 次正文生成、12 次独立维护评估和 1 次统一评分，使用现有 Codex 额度。临时 Git 操作由执行器完成，模型始终在只读沙箱中；不修改、提交或推送真实项目。

中止时保留样本及错误，使用 `--resume <中止结果>` 并指定新的 `--output` 文件继续；只有用例、脚本、模型、CLI 和规则哈希均未变化时可复用。每组每例单次生成只构成小型先导评测，不能推导生产中的稳定收益。

## 评分材料修复记录

[首轮记录](handoffs-2026-09-23.json)保留全部 6 份正文、12 份维护回答及最初评分。初次判卷材料只包含文件、diff 和提交说明，遗漏了模型实际读取的提交号、分支、工作区状态及父提交说明。因此评审将这些真实信息误判为无依据断言，所有维护回答的证据边界项都被判失败。

修复只补充这些 Git 元数据：由同一用例和同一提交说明重建每个读者仓库，并核对完整快照与原记录一致。没有增加该组看不到的业务背景。所有生成输出、用例、评分项、评审指令、模型和样本顺序保持不变，重新评审写入[独立文件](handoffs-2026-09-23-regraded.json)；原结果不覆盖。执行器已将此证据补全纳入常规评分步骤。
