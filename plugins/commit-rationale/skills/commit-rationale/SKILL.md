# Commit Rationale

结合当前上下文判断正文是否必要，只保留有依据、无法从代码和最终 diff 恢复、且影响后续维护的信息。

## 裁决

1. 阅读仓库要求、近期提交风格和本次实际 diff（含文档），确认提交范围，区分暂存、未暂存和无关改动。
2. 回顾当前任务的需求、约束、决策和实际验证结果；只查相关资料，不根据 diff 猜测作者动机。
3. 对候选正文逐句问：**删掉它，维护者会漏掉什么具体约束、误判什么取舍，或高估什么验证结论？**没有具体影响就省略。

做法已写明，不代表其原因已记录；原因已被改动表达时也不重复。“曾经发生过”“用户提出过”仅说明来源，本身不构成维护价值。完成筛选后可以只写标题，无需为凑正文编造背景或逐项追问。

## 写作

- **标题**：简洁描述最终改动，遵循用户指定的语言和仓库风格。
- **正文**：与标题空一行，自由表达，不设必填章节。起草后逐句对照最终 diff，删除复述、流水账和空洞表态；混合句只保留有价值的补充信息。不写筛选过程、原始聊天、内部推理记录或敏感资料。
- **验证**：仅保留影响维护判断的结果或缺口，区分亲自观察与用户报告，说明适用范围；不得把计划写成通过，或将旧代码的验证结果套用到最终代码。
- **Trailers**：可选，使用 Git 原生支持，在末尾独立成段。只写已知稳定引用或有依据的标准元数据，不编造编号、署名或背书。默认不添加 Agent、上下文版本、模型或会话字段；明确要求除外。Agent 代为提交不代表其编写了代码。

## merge、squash、amend

把新提交作为独立阅读入口，先完整读取相关源提交的标题、正文和引用，再确定最终 diff：

- **merge**：读取本次新引入的提交，包括其中的合并提交；已完成的普通双亲合并 `M` 可用 `M^1..M^2` 限定范围。对照第一父提交到最终合并结果的 diff，并纳入有价值的冲突处理或集成决策。
- **squash**：读取被压缩范围的提交说明，对照压缩基线到最终结果的 diff，按最终行为组织背景，不沿用中间提交的叙事顺序。
- **amend**：读取原提交说明，以原第一父提交（初始提交用空树）到修订后结果的差异为整体，不能只根据本次新增的暂存 diff 写正文。

结合源说明和当前上下文重新生成标题与正文：提炼仍适用、且未被最终代码和 diff 充分表达的约束、取舍和验证边界，让读者不必遍历源历史才能理解关键背景。原提交仍可追溯，不是省略有价值正文的理由。

不拼接全部原文；合并相同事实，删除过时信息，保留适用的引用与背书，不扩大验证范围。约束相互矛盾时先核实，不靠猜测抹平。筛选后确无有价值背景时，仍可只写标题。

## 执行

- 只请求说明时返回草稿，不改仓库。执行 Git 操作遵循仓库流程和已有授权，仅处理授权文件或 hunk，不擅自扩大到改写历史或推送，也不因使用技能再次确认。
- 提交前核对暂存 diff 与说明。多行说明通过临时 UTF-8 文件传给 `git commit -F`，避免 shell 插值并在结束后清理文件。遵守 hook 和签名要求，失败后先检查结果，不绕过或盲目重试；成功后核对实际说明与 diff，报告提交 ID、验证范围和剩余改动。

## 示例

“联调发现超时，于是把三秒改成五秒”没有额外决策依据，可省略。若代码和 diff 未体现、但上下文已确认上游日结耗时三到四秒、客户端期限为五秒，则保留这些限制，说明超时为何不能继续增大。
